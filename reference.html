/<cost_topic>profile.yamlstd_msgs/ Float32MultiArraycost evaluator → HIL optimizer[k, cost]: mean of the per-cycle costs over gait_cycles_to_consider cycles, after skipping gait_cycles_to_skip; k = 0 in Deployment.
HIL optimizer: hil (×H, one per profile in HIL mode)
/<hil_output_topic>profile.yamlstd_msgs/ Float32MultiArrayoptimizer → profile node[k, p1 … pn]: candidate number and one parameter per optimized dimension; a new candidate follows each cost it accepts. On stop, every round and the best candidate are written to ~/exo_stack_resources/hil_results/.

All ExoCore topics use best-effort reliability, and the hubs publish and subscribe best-effort over micro-ROS.

k ties the HIL messages together: the cost evaluator counts only cycles of the candidate in profile_status, and the optimizer accepts only a cost carrying the k it proposed.

ExoStack uses standard message types only, so no custom message package has to be built for micro-ROS.

Known limitations of v1.0

KNOWN LIMITATIONS OF v1.0
  • Device-list values dev_misc_data and dev_misc_data2 reach the I²C drivers that read them (the BNO085 channel count); the NAU7802 calibration and the AS5600 direction pin come from the drivers' registration lines.
  • Function profiles (Builder1_Function with PolynomialFunction or CubicPolynomialFunction) and PCHIPInterpolatedList do not run in v1.0; use a _List builder with LinearInterpolatedList.
  • PASE writes the approach gait_phase, which the planner does not recognise, and adds init_points and gp_params to Bayesian profiles, which OPT_BAYESIAN does not accept: configure phase-based planners and Bayesian profiles in the YAML files.
  • The I²C registry holds 8 entries, all used by the shipped drivers (§2.5).
Corrections are planned for the next release.
